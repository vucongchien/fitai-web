# FITAI acceptance scenarios

## Activation

1. A signed-out user sees only Google and Facebook authentication actions.
2. A successful preview or OAuth callback enters onboarding.
3. Invalid body measurements, no equipment, no focus area, or no available day blocks progress with a field-specific message.
4. Onboarding draft data survives refresh in the same browser tab and is not written to long-lived local storage.
5. Planning presents named backend stages without fabricated percentages and never blindly retries roadmap creation.

## Daily training

1. Home exposes one dominant next-session action and streams secondary evidence independently.
2. Roadmap communicates planned, next, completed, and recovery states through text, shape, and color.
3. Session preparation explains duration, effort, exercises, safety, and Manual Mode before starting.
4. Live Workout logs a set, captures RPE in words, starts a rest interval, and advances to the next exercise.
5. Offline state preserves the set inputs and disables submission rather than claiming the set was saved.
6. Reporting injury stops the workout before collecting more details.
7. Summary renders only contract-backed totals and explicitly says why a manual workout has no form score.

## Progress and profile

1. Progress charts have direct labels and text summaries and never rely on color alone.
2. Profile changes that affect the roadmap explain schedule impact before regeneration.
3. Injury report and recovery state use separate destructive and recovery semantics.

## Motion and accessibility

1. Home session marker morphs to preparation when the destination is ready.
2. Planning, effort, and recovery colors transfer visual ownership at the correct stage.
3. Reduced-motion removes positional movement while preserving navigation and state changes.
4. Header and bottom navigation remain stable during route transitions.
5. All controls are keyboard reachable, visibly focused, and at least 48 by 48 CSS pixels on mobile.
